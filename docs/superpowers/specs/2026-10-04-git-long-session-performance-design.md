# 장기 사용 시 Git 지연을 줄이는 설계

상태: 검토 초안. 제품 코드 구현 전 사용자 검토 대상.

## 목적과 완료 조건

사용자가 요청한 결과는 장시간 사용해도 변경 목록과 그래프가 계속 느려지지 않는 것이다.
불필요한 Git 조회와 오래 멈춘 프로세스를 정리하며, 사용자 전역 설정과 워크스페이스 설정을 제공한다.
사용자가 추가로 요청한 "놀고 있는 Git 프로세스 정리 옵션"은 자동 정리 토글·유휴 시간·수동 정리 명령으로 제공한다.
Mac과 SentinelOne의 재시작이나 관리자 인증에 의존하지 않고 확장에서 제어 가능한 병목부터 해결한다.

완료 판정에는 다음 증거가 모두 필요하다.

1. 실제 저장소의 staged/unstaged/untracked 파일, rename, branch 상태가 기존 Git 출력과 일치한다.
2. 변경 목록·그래프·Tab Manager가 동시에 같은 상태를 요구해도 중복 전체 상태 조회를 피한다.
3. 화면·문서·저장소 전환으로 쓸모없어진 확장 소유 조회가 종료되고, 오래 멈춘 읽기에는 제한 시간이 적용된다.
4. 반복 새로고침·화면 전환 후 확장 소유 Git 프로세스 수와 listener/timer가 누적되지 않는다.
5. 큰 실제 저장소에서 동일 기능을 유지하며 반복 조회 시간이 감소한다. 단위 테스트 통과만으로 성능 개선을 판단하지 않는다.
6. 수정 버전을 커밋·푸시·로컬 설치·vsce publish 하고 실제 확장 호스트에서 동작을 확인한다.
7. 사용자에게 남는 OS 보안 계층 대기가 있으면 내부 Git 시간과 구분하여 기록하고 계속 원인을 좁힌다.
8. 유휴 정리 옵션의 사용자 전역·워크스페이스 값과 상속 상태가 표시되고, 옵션을 끄면 주기 정리가 중단된다. 쓰기 작업·필요한 조회·다른 사용자의 프로세스는 정리되지 않는다.

## 확인된 근거

- 현재 버전은 0.1.72073이다. Graph에는 읽기 취소가 적용됐지만 blame·상태·통계의 일부 경로에는 전달되지 않는다.
- payroll의 전체 상태 조회는 2.46초, 미추적 탐색을 제외하면 0.16초였다.
- 실제 index는 과거 fsmonitor 토큰을 보관해 추적 파일 31,773개를 반복 검사했다.
- 임시 index에서 untracked cache와 normal 상태 모드를 사용하면 동일한 payroll 변경 결과가 2.95초에서 0.14초로 줄었다.
- all 상태 모드는 임시 index에서도 디렉터리 탐색 비용이 남았다. normal 모드의 디렉터리 결과를 그대로 파일 목록에 넣으면 기능이 축소되므로 추가 열거가 필요하다.
- GSC Changes는 porcelain v1/all, Graph는 porcelain v2/branch, Tab Manager는 porcelain v1/branch/all을 각각 읽는다.
- Git Blame Annotations 0.5.3은 활성 파일 변경마다 메뉴 상태용 git status를 실행하며 취소·시간 제한·캐시가 없다.
- 초기 점검의 Git 9개와 03:34 UTC 점검의 Git 16개는 사용 중인 저장소의 fsmonitor였고 멈춘 일반 Git은 없었다. 프로세스 수나 실행 나이만으로 종료 대상을 결정할 수 없다.
- 실제 저장소 10곳에서 표준 Git 명령으로 성능 메타데이터를 갱신했고, staged 항목·HEAD·전체 변경 목록이 보존됐다. imgflash의 일반 조회는 1.60초에서 69~79ms, 전체 조회는 2.18초에서 712~763ms로 줄었다.
- split/sparse index, submodule, linked worktree, SHA-256, 최초 커밋 전 상태, merge 충돌의 진단용 캐시 경로는 기존 Git 목록과 일치했다. 제품 구현과 장기 사용 검증은 아직 남아 있다.
- 03:22 UTC 점검에서 스왑 약 2.1GB와 메모리 압축·병렬 빌드 활동이 관찰됐다. Git 지연과의 직접 관계는 확인되지 않았고 앞선 파일 핸들 점검에서 고갈은 없었다.
- 재부팅 전에는 Git 진입 이전의 EndpointSecurity 실행 승인 대기가 관찰됐다. 담당 보안 제품은 아직 분리하지 못했다.

## 접근 방식

기존 실행기·Git 서비스·상태 공급자에 아래 기능을 단계적으로 연결한다.
전역 Git 동시 실행 수를 일괄 제한하는 방식은 현재 병목을 해결한다는 증거가 없으므로 선택하지 않는다.
공유 상태 조회와 소유권 기반 취소로 실제 불필요한 실행을 줄이고, 캐시가 반복 파일 탐색을 피하도록 한다.

## 1. 확장 소유 Git 실행 수명

- `git/`에 실행 수명 도우미를 두고 문자열·Buffer·stream 실행에서 공통 사용한다.
- 실행 목적, 저장소, PID, 시작 시각, 요청 소유자를 기록한다. 명령 인자의 인증 값과 전체 환경은 로그에 기록하지 않는다.
- 조회 전용 명령에 기본 30초 제한을 적용한다. 사용자 전역/워크스페이스에서 변경 가능하게 한다.
- commit, merge, rebase, checkout, apply, fetch, push 등 상태를 바꾸거나 hook을 실행하는 작업은 조회 제한의 대상에서 제외한다.
- 취소 또는 제한 시간 도달 시 소유한 조회에 SIGTERM을 보내고, 1초 뒤 살아 있으면 SIGKILL을 보낸다.
- 자식 실행이 종료됐음을 확인한 뒤 실행 기록과 timer/listener를 제거한다. 종료 요청만으로 실행 슬롯을 반환하지 않는다.
- hook·외부 도구 자식이 포함될 수 있는 조회는 소유한 프로세스 그룹의 범위를 검증한다. 다른 확장·터미널의 작업을 종료하지 않는다.
- 종료가 실패하거나 커널 대기 때문에 지연되면 PID와 대기 시간을 OUTPUT에 기록하고 후속 조회가 무제한으로 겹치지 않게 한다.

## 2. 공유 작업 상태 스냅샷

- 저장소 루트별로 하나의 상태 스냅샷 서비스가 branch/HEAD, staged, unstaged, untracked 목록을 소유한다.
- 동일 세대의 진행 중 조회를 공유한다. 완료 값은 짧은 기간 재사용하고 파일·index·HEAD 변경이나 명시적 새로고침에 무효화한다.
- `force` 요청이 겹치면 무한한 동시 조회를 만들지 않고 진행 중 결과 뒤에 필요한 최신 세대 한 번을 실행한다.
- Graph는 공유 결과에서 가상 커밋 여부를 읽고 Changes는 파일 목록을 읽는다. 서로 다른 porcelain 형식 때문에 별도 status를 실행하지 않는다.
- 소비자마다 취소 신호를 연결한다. 다른 소비자가 사용 중인 공유 실행은 유지하고 마지막 소비자가 해제되면 취소한다.
- 기존 최신성 fence와 mutation 직후 검증 정책을 유지한다. 늦게 끝난 결과가 최신 목록을 덮지 못한다.
- 라인 통계는 스냅샷 조회와 별도로 지연 실행하며, 사용자가 떠나면 진행 중 통계도 취소한다.

## 3. 전체 파일 목록을 보존하는 캐시 경로

- 실제 index와 Git 설정을 변경하지 않는 확장 소유 임시 index를 사용한다.
- 실제 index가 바뀌면 임시 index를 다시 준비한다. 원본의 내용·mtime/size를 조회 전후 확인하고 조회 중 변경은 새 세대로 재시도한다.
- command scope에서 임시 index에만 untracked cache를 활성화하고 cache 갱신 쓰기를 허용한다.
- 정상 상태 조회는 porcelain v2, branch, no-ahead-behind, untracked-files=normal로 실행한다.
- normal 결과의 미추적 디렉터리를 모아 경로 제한된 ls-files --others --exclude-standard -z로 파일을 추가 열거한다.
- 추가 열거는 literal 경로를 사용하고 한 명령의 인자 크기를 제한한다. 중복 결과를 제거하고 모든 파일 이름과 상태를 보존한다.
- 미추적 파일과 경로별 열거 결과도 파일 이벤트·fsmonitor 변화에 맞춰 무효화한다.
- split/sparse index, submodule, linked worktree, index 교체, 매우 큰 인자, fsmonitor 실패는 정확성을 먼저 검증한다. 지원되지 않는 경우 authoritative 전체 조회로 복구하고 이유를 로그에 남긴다.
- 임시 index를 쓰는 기존 commit/rebase/split 작업의 GIT_INDEX_FILE 환경을 덮지 않는다.
- 상태 스냅샷 해제 시 임시 파일과 진행 중 열거를 정리한다. 삭제 대상은 확장이 생성한 디렉터리로 제한한다.

## 4. 자동 조회 소비자와 blame

- blame 서비스에 취소 신호를 전달하고 라인 표시와 블록 CodeLens가 같은 파일의 유효한 조회를 공유한다.
- 문서 닫기·버전 변경·기능 끄기·extension dispose 시 필요 없어진 실행을 취소한다.
- CodeLens의 VS Code CancellationToken을 실제 Git 실행 수명에 연결한다.
- 현재 설정상 표시되는 파일과 기능에만 조회를 요청한다. 활성 파일·HEAD·파일 내용이 같은 반복 이벤트는 캐시를 사용한다.
- Git Blame Annotations의 자동 조회는 별도 확장 코드에서 확인된 문제다. 실제 사용하는 기능 여부를 확인해 해당 확장의 수정 또는 비활성화 방법을 별도로 선택한다.

## 5. Tab Manager의 공유 상태 연결

- 기존 GSC 공개 API의 비교 계약을 유지하고 선택적인 상태 공급자 계약을 추가한다.
- Tab Manager가 이 계약을 지원하는 GSC를 찾으면 같은 상태 스냅샷을 사용한다.
- GSC가 설치되지 않았거나 오래된 버전이면 독립 CLI 공급자를 계속 사용할 수 있다.
- 상태 공급자의 event/dispose/취소 경계를 명시하고 확장 종료·workspace 변경 때 구독과 조회를 해제한다.
- 열린 탭, 활성 Git 필터, 표시 중인 Explorer 등 소비자가 필요로 하는 범위로 자동 조회를 줄인다.
- 초기 한 번의 상태 조회가 느리다고 저장소 자체가 사라지지 않도록 탐색과 상태 로딩의 오류를 구분한다.

## 6. fsmonitor 정리와 설정

### 설정과 명령

| 설정/명령 | 기본값 | 사용자에게 보이는 동작 |
| --- | --- | --- |
| `gitSimpleCompare.gitProcessCleanup.enabled` | `false` | 유휴 Git 프로세스의 주기 자동 정리를 켜거나 끈다. |
| `gitSimpleCompare.gitProcessCleanup.idleMinutes` | `5` | 감시 프로세스를 정리하기까지의 유휴 시간. 1~1440분 범위에서 설정한다. |
| `gitSimpleCompare.cleanupIdleGitProcesses` | 수동 명령 | 정리 가능한 프로세스를 조회하고 선택한 대상만 정리한다. 자동 정리가 꺼져 있어도 실행할 수 있다. |

- 설정은 사용자 전역과 워크스페이스에 각각 저장할 수 있으며 워크스페이스 값이 우선한다. 저장소별 정책 해석에는 기존 resource 설정 경계를 사용한다.
- 자동 정리 기본값은 꺼짐이다. 켜면 1분 간격으로 후보를 점검하고 기본 5분 유휴 기준을 적용한다. 끄면 주기 작업과 아직 실행되지 않은 정리 요청을 해제한다.
- 30초 조회 제한과 화면·문서 해제에 따른 읽기 취소는 실행 수명의 별도 정책이다. 유휴 정리 토글을 끈다고 dispose 이후 불필요한 조회를 남기지 않는다.
- 조회 제한 시간, 불필요한 읽기 취소, 공유/캐시 상태 경로의 설정도 사용자 전역·워크스페이스 범위로 제공한다.

### 정리 대상 판정

- 조회 프로세스는 확장이 등록한 실행 기록과 소비자 해제 상태로 판정한다. 아직 필요한 조회는 유휴 후보로 표시하지 않는다.
- 감시 프로세스는 확장이 사용한 저장소와 확인 가능한 소유권을 기준으로 판정한다. 마지막 Git 사용 시각을 기록하며, 진행 중인 읽기·쓰기나 소비자 사용이 있으면 유휴 시간을 갱신한다.
- 자동 정리는 확장 소유가 확인된 조회와 감시 프로세스로 한정한다. 수동 명령은 별도로 발견한 감시 프로세스도 저장소 사용 여부와 소유권을 확인할 수 있을 때만 후보로 제시한다.
- PID, 시작 시각, 사용자 ID, 저장소, 소켓 위치를 확인하고 실제 종료 직전에 다시 대조한다. PID가 재사용됐거나 소켓 매핑이 달라지면 정리를 건너뛴다.
- VS Code 다른 창, 터미널, 작업 프로세스에서 저장소가 사용 중이면 감시 프로세스를 유지한다. 매핑이나 사용 여부가 불명확한 경우에도 유지한다.
- CPU 0%, 프로세스 나이, 출력이 없는 시간만으로 유휴·멈춤을 판정하지 않는다. commit·merge·rebase·checkout·fetch·push 및 hook을 실행하는 작업은 유휴 정리 대상에서 제외한다.
- 감시 프로세스는 공식 `git fsmonitor--daemon stop`으로 종료한다. 종료 후 다음 Git 사용 시 정상적으로 다시 시작할 수 있어야 한다. index·lock·객체·캐시 파일을 삭제하지 않는다.
- 확장 소유 조회의 종료는 1절의 취소·종료 확인 정책을 사용한다. 소유권 검증이 구현되지 않은 OS 경로는 자동 정리를 건너뛰고 이유를 기록한다.

### 기존 설정 UI와 상태 표시

- Changes의 기존 Git 설정 메뉴에 사용자 전역 토글과 워크스페이스 토글을 두고, 현재 값·상속 상태·유휴 시간·지금 정리 명령을 연결한다. 기존 체크 표시, command title/shortTitle, busy context 패턴을 재사용한다.
- 수동 명령은 저장소·PID·종류·유휴 시간을 보여준다. 목록 조회와 정리 중에는 진행 상태를 표시하고 중복 실행을 막는다. 선택 화면을 취소하면 종료 명령을 실행하지 않는다.
- 후보가 없으면 "No idle Git processes to clean."을 표시한다. 일부만 종료되면 정리 수와 유지 수를 표시하고 유지·실패 이유는 OUTPUT에서 확인할 수 있게 한다.
- 정리 도중 저장소가 사용되면 해당 대상을 유지한다. 부분 실패가 다른 대상의 결과를 지우지 않도록 한다.
- UI 기본 영어와 한국어 번역을 제공하고 모든 버튼·아이콘·메뉴 액션에 tooltip 또는 명확한 command title과 접근성 이름을 제공한다. 긴 저장소 경로는 기존 축약 표시와 전체 경로 tooltip을 사용한다.
- OUTPUT에는 후보 발견·유휴 시간 갱신·정리 시작·종료 확인·활성 작업 보호·소유권 불명·설정 해제·실패 원인을 기록한다. 전체 명령 인자와 환경은 기록하지 않는다.

## 검증과 출시

- 실행 수명: 정상 종료, 취소, 시간 초과, SIGTERM 무시, 중첩 자식, spawn 오류, 종료 직전 경쟁, timer/listener 해제를 실제 자식 프로세스로 확인한다.
- 상태 정확성: staged/unstaged, rename/copy, 삭제, 미추적 디렉터리, 공백/개행/선행 하이픈 경로, linked worktree, split/sparse index, submodule, index 변경 경쟁을 Git 원본 출력과 비교한다.
- 공유: Changes/Graph/Tab Manager 동시 요청의 status 실행 횟수, 소비자별 취소, mutation 직후 최신성, stale 결과 폐기를 확인한다.
- 성능: payroll/vcmninth/GSC 저장소에서 냉·온 캐시, 전체 목록, 반복 새로고침을 같은 조건으로 비교한다. 임시 index 실험 결과만으로 설치 버전 성능을 주장하지 않는다.
- 장기 사용: 반복 문서 전환·열기/닫기·그래프 열기/닫기와 유휴 후 복귀에서 소유 프로세스/캐시/구독 수가 안정적인지 확인한다.
- 유휴 정리: 옵션 켜기/끄기, 사용자 전역·워크스페이스 우선순위, 유휴 시간 변경, 후보 없음, 선택 취소, 부분 실패, 다른 창·터미널 사용, PID 재사용, 공식 daemon stop 이후 Git 재사용을 검증한다. 토글 해제와 dispose 이후 주기 timer와 정리 요청이 남지 않아야 한다.
- UI: 설정 범위와 토글 동작의 기능 QA, 실제 렌더링의 시각 QA를 각각 수행한다.
- 빌드·타입 검사·관련 회귀 테스트·실제 확장 호스트 검증 뒤 버전업·커밋·푸시·로컬 설치·vsce publish한다.
- 출시 후에도 Git 실행 전 대기와 Git 내부 탐색 시간을 구분해 측정한다. 장기 사용 증상이 남으면 목표를 완료로 표시하지 않고 해당 병목을 계속 추적한다.

## 경계와 미확정 사항

- SentinelOne 등 보안 서비스의 정책·인증·큐를 변경하는 기능은 이 확장 설계에 포함하지 않는다.
- 정상적으로 사용 중인 다른 프로그램의 Git 쓰기 작업에는 종료 정책을 적용하지 않는다.
- Git Blame Annotations 기능 사용 여부와 운영체제 보안 대기의 담당 클라이언트는 아직 확인이 필요하다.
- PID만으로 소유권을 추측하지 않는다. OS별 그룹 종료·fsmonitor 사용 여부 검증이 확보되지 않은 경로에서는 자동 정리를 건너뛰고 기록한다.
