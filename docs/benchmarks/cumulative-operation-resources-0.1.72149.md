# 전체 작업 누적 비교와 작업 구간 RSS — 0.1.72149

정상 Graph 기준 `b9d8ed66f58156095e094f2ec1d5e4ac4d07cd9b`(0.1.72112)와 현재 배포
`099d6978aa0dc5cf9e625697abc6cdee6024e2ee`(0.1.72149)의 누적 비교다.
이번 작업은 계측·검증 보강이며 제품 런타임 변경이나 새로운 배포의 성능 효과가 아니다.
원래 전체 목표는 **진행 중**이다. 이번 기본 시간 비교는 오히려 느려졌으며 이를 제외하지 않는다.

## 범위와 입력

독립 소유 fixture의 1,000파일·1,000commit·100branch·공유 upstream 8개에서
18개 변형을 같은 순서로 실행했다. initial, 새/기존 upstream push,
pull/fetch의 신규·알려진·무변경 이력, rebase, squash/no-ff merge,
PR squash/replay, cherry-pick, loaded/unloaded checkout이다.

각 mode는 **B/A/A/B**, source별 2개 실행이다. 기본 시간·CPU·메모리 mode는 분리했다.
총 **216개** 정식 비교가 Native HEAD·부모·refs·local-only와 production HTML/CSP/JS의 DOM에
일치했다. 추가 명령 시간 진단 6건도 통과했다. 사용자 버튼이나 GitHub 네트워크 시간 비교는 아니다.

loaded checkout은 양쪽 첫 페이지에 실제 표시된 같은 Native topic을 사용한다.
loaded/unloaded 양쪽 branch+tree fingerprint가 12개 실행에서 동일함을 검사했다.
이는 이전 비교에서 source별 목록 순서로 다른 대상을 선택하던 입력 차이를 해소한다.
제품 소스·media는 배포 0.1.72149와 같고, 현재 쪽 6개 bundle hash도 모두 같다.
이전 쪽 raw bundle은 archive의 임시 경로가 달라 hash가 바뀐다.
같은 고정 source를 두 경로에 빌드해 basename만 치환하면 바이트가 같음을 별도로 확인했다.

## 새 메모리 계측

`sample-phase-memory.py`는 작업 시작 전 첫 표본과 끝의 마지막 표본을 포함해 소유 프로세스만 수집한다.
benchmark Node, Chromium SystemInfo에서 확인한 PID와 자손, 나머지 소유 자손을 구분한다.
관찰자와 ps 자체는 합산에서 제외하며, 실패/부분 관측을 성공으로 세지 않는다.
`PhaseMemorySampler.stop()`은 observer의 실제 close를 기다리고 중복 중지를 허용한다.

원시 표본은 구간 종료 뒤 별도 파일에 기록하고 SHA-256으로 묶는다.
benchmark의 다음 작업에는 작은 요약만 남겨 표본 배열 누적을 피한다.
구성요소별 서로 다른 시점의 최대값을 합치지 않고 같은 시점 합산 RSS의 최대 표본을 선택한다.

메모리 72개 구간에서 총 415개 표본, 구간당 최소
4개를 받았다. 요청 간격은 50ms지만 실제 최장 간격은
168.008ms였다. 짧은 자식이나 표본 사이 peak를 놓칠 수 있다.
합산 RSS는 공유 page를 중복 계산할 수 있어 실제 물리 메모리·retained heap·정확한 peak가 아니다.
첫/마지막 표본에는 짧은 counter 준비·정리 구간도 포함된다. fixture 준비·Native 사후 oracle은 제외한다.
메모리 mode의 CPU/시간은 관찰 부하가 있어 진단용으로만 보관한다.

기존 별도 CPU mode는 Node/Playwright, 종료·wait된 Native 자식과 완전한 PID Chromium delta를 합친다.
메모리 observer는 이 mode에서 시작하지 않는다. probe 빌드·fixture·Native oracle은 CPU 구간 밖이다.

## 시간 관측의 한계와 추가 진단

Graph 관측은 서비스 완료 시각 뒤 마지막 일치 Graph 모델 paint까지다.
paint가 없는 unchanged 상태는 host의 갱신 판단 완료를 사용하도록 했으며 이번 표본에는 0건이었다.
별도 tagStatus·메뉴·버튼 상태의 표시 완료 시각을 전부 포괄하는 값은 아니다.
이 데이터의 기능적 정확성은 settle 뒤 확인하지만 paint timing 범위를 넓혀 해석하지 않는다.

추가 tracked push·pull·무변경 fetch 진단도 더 느린 현재 표본을 그대로 보존한다.
특히 무변경 fetch는 이전 서비스 55ms/명령 완료 54ms, 현재 224ms/223ms였다.
현재 pull은 1411ms 중 pull 명령 완료 구간이 1215ms였다.
명령 probe는 spawn부터 pipe close와 registry 정리까지 포함하며 순수 OS 실행만의 값이 아니다.
명령 준비 JS만 원인이라고 판단하거나, 이를 제품 회귀나 외부 부하 중 하나로 단정하지 않는다.
공통 완료 구간의 exit·pipe close·ownership 정리를 분리하고 visible metadata의 최종 frame을
함께 관찰하는 것이 다음 조사 범위다. 안전 검사를 생략하는 변경은 만들지 않았다.

## 검사와 보존

실제 64MiB/32MiB 할당 자식의 RSS·분류, 관찰자 제외와 종료, 잘못된 입력 거부,
동시 최대값과 원시 파일 분리, 기존 observer의 인자 보유 방지 검사 등 **6개**와 타입 검사가 통과했다.
독립 실제 Git/Graph smoke에서 기준/현재의 초기 로드·같은 checkout 입력과 파일 저장도 확인했다.
Native RSS 계측은 POSIX용이며 Windows에서는 해당 Native 검사를 skip한다. 이번 macOS 검사는 skip 0건이다.
프런트엔드 소스·스타일·문구는 변경하지 않았다. 현재 설치된 제품 런타임은 0.1.72149다.

Captain·사용자 stash·snapshot·보존 PR worktree는 변경하지 않았다.
OS 포커스 전환, foreground Host, 강제 reload, 별도 Marketplace 상태 점검을 하지 않았다.
원시 표본·실행·명령 진단·고정 source·bundle 경로 증명의 hash는 같은 이름의 JSON에 보관한다.
