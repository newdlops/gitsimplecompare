# GitHub 통신 성능 개선 구현·판정

구현과 검증을 완료했다. 기본 CLI 경로에서도 반복 목록·상세 재열기·검색은 빨라졌다.
직접 HTTP는 지원 환경에서 추가 이득이 있으며 목록의 효과는 작다. native 사전 인증은 push dry-run만 이득이 확인되어 기본 꺼짐을 유지한다.
[전체 표본과 동등성 SHA](./github-http-performance-20261101.json) · [검증 기록](./github-http-verification-20261101.json) · [재현 스크립트](../../scripts/benchmark-github-http.mjs)

## 구현 범위

- PR 상세 파일은 검증된 저장소·실제 인증 정보·head/base·파일 수가 같은 완전한 응답만 재사용한다. 댓글과 리뷰는 다시 읽는다.
- 반복 목록은 얕은 응답을 먼저 표시하고 변경 가능한 metadata를 갱신한다. 커밋 제목과 파일 수는 불변 identity가 일치할 때 재사용한다. 검색도 같은 인증·저장소 문맥과 전송 경로를 사용한다.
- 직접 HTTPS는 Node 18의 연결 pool을 사용한다. 인증 정보는 논리적 조회마다 새로 획득하며 페이지 사이에서 고정한다. 취소·종료·redirect·압축 응답·rate limit·메모리 상한을 검사한다.
- 지원이 확인되지 않은 프록시·CA·호스트·Agent 정책은 요청 전에 CLI를 선택한다. 실제 VS Code의 기본 `http.proxySupport=override`는 CLI 경로다. 검증된 `on` 정책은 격리된 테스트 프로필에서만 사용했다.
- native Git 사전 인증은 별도 고급 설정이며 기본값은 `false`다. Git이 선택한 credential helper를 사용하고 명시적 인증 설정, hook, 승인된 source와 lease를 보존한다.

## 측정 방법

기준은 `706d1c2a6c8b2d5c01e45e12735e5590572a43aa`, 측정 커밋은 `282dc52ffae979f6a472892c2469e521d028b58c`이다.
제품 코드는 전체 검사를 통과한 `1162cbb2d5ef1351924a159e12adca48086f14d1` 이후 바뀌지 않았으며, 이후 커밋은 측정 fixture만 보완한다.
같은 macOS arm64 / Node 22.22.2, GitHub CLI 2.95.0, Apple Git 2.50.1에서 각각 일곱 쌍을 순서 교대해 측정했다. 최종 기록 시각은 2026-11-01 09:18:29 UTC다.
공개 `cli/cli`의 목록·검색과 PR #14848의 738개 파일을 사용하며 실제 제품 `PullRequestService.getDetail` 호출을 포함한다.
임시 읽기 저장소의 origin과 `GH_REPO`를 모두 `cli/cli`로 맞추고, 측정 전에 `gh repo view`의 저장소 이름도 확인한다.
초기 측정은 두 저장소 선택이 달라 DTO 일치 검사에서 실패했으며 최종 근거에서 제외했다. 사용자 저장소의 remote는 바꾸지 않았다.

수정 전후 비교는 CLI끼리 수행한다. 이 결과가 기본 VS Code 정책에서 적용되는 캐시·쿼리 개선이다.
전송 비교는 같은 수정 코드와 예열된 불변 snapshot을 유지한 채 논리적 조회별 CLI/HTTP 정책만 바꾼다.
이는 Settings 변경 시간을 측정하지 않는다. 실제 Settings 변경은 읽기 세대를 새로 시작한다.

인증 획득은 각 측정의 전체 시간에 포함한다. 수정 경로의 `gh auth token` 프로세스 수와 시간도 별도로 기록한다.
기준 CLI와 cold 경로의 별도 token 프로세스 수가 0이라는 것은 CLI 내부 인증 시간이 없다는 뜻이 아니다. 그 시간도 전체 측정에 포함한다.
`apiReads`는 CLI의 `api`/`repo view` 실행 수와 직접 HTTP의 실제 종료 이벤트 수다. CLI 값은 패킷 캡처가 아니다.
첫 표시는 제품 progress callback의 최초 호출이며, 별도 progress가 없는 검색은 완료 시간과 같다.
숨겨진 준비 요청과 quota 확인은 측정 표본에 포함하지 않는다. quota가 부족하면 reset까지 기다리고 그 이력을 남긴다.

각 쌍의 전체 DTO를 key 순서만 정규화해 비교하고 SHA-256을 저장한다. 배열 순서와 모든 파일·커밋·댓글을 보존한다.
native Git은 소유한 임시 저장소만 사용하며 push는 항상 `--dry-run`이다. 사용자 저장소의 HEAD/index/config와 임시 저장소의 HEAD/config 보존을 검사한다.
native fixture는 shallow·blobless·최신 상태이며 두 모드에 같은 빈 로컬 hooks 디렉터리를 사용한다. 실제 객체 업로드나 사용자 hook 실행 시간은 측정하지 않는다.
인증 헤더·토큰·원격 본문·Git trace 원문은 결과 파일에 저장하지 않는다.

## 기본 CLI 경로의 수정 전후

단위는 ms, 일곱 표본의 중앙값이다. 개선 쌍은 같은 순서 번호에서 수정 경로가 빨랐던 횟수다.

| 구간 | 이전 완료 | 수정 완료 | 이전 첫 표시 | 수정 첫 표시 | 조회 수 이전→수정 | 완료 개선 쌍 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 첫 목록 | 4,581.4 | 4,441.9 | 946.1 | 998.6 | 6→6 | 3/7 |
| 반복 목록 | 6,007.8 | 3,237.3 | 6,007.4 | 866.6 | 1→5 | 7/7 |
| 738파일 상세 재열기 | 6,336.4 | 683.0 | 793.2 | 681.7 | 9→1 | 7/7 |
| 검색 | 1,623.2 | 1,121.4 | 1,623.2 | 1,121.4 | 3→2 | 7/7 |

반복 목록은 전체 46.1%, 첫 표시 85.6% 감소했다. 조회는 늘었지만 얕은 root와 병렬 metadata로 무거운 단일 응답 대기를 줄였다.
상세 재열기는 전체 89.2% 감소했고, 검색은 30.9% 감소했다. 세 구간 모두 일곱 쌍에서 빨라졌다.
첫 목록은 완료 중앙값 차이가 3.0%에 그치고 3/7쌍만 빨랐으며 첫 표시 중앙값은 더 느렸다. cold 개선은 입증하지 않는다.
반복 목록·상세·검색의 별도 credential 획득 중앙값은 각각 46.2 / 52.5 / 55.8ms이며 위 시간에 포함했다.

## 같은 수정 코드의 CLI와 직접 HTTP

두 모드 모두 실제 인증 획득을 포함한다. 불변 snapshot과 DTO는 같으며 조회 수도 동일하다.

| 구간 | CLI 완료 | HTTP 완료 | CLI 첫 표시 | HTTP 첫 표시 | 조회 수 | 완료 개선 쌍 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 반복 목록 | 3,232.3 | 3,104.5 | 956.1 | 868.8 | 5→5 | 6/7 |
| 상세 재열기 | 703.0 | 568.7 | 702.6 | 567.5 | 1→1 | 6/7 |
| 검색 | 997.9 | 833.4 | 997.9 | 833.4 | 2→2 | 6/7 |

HTTP는 완료 중앙값이 각각 4.0 / 19.1 / 16.5% 감소했다. 전체 56개 직접 요청 중 52개가 연결을 재사용했고 새 연결은 4개였다.
HTTP의 별도 credential 획득 중앙값은 각각 49.1 / 42.0 / 44.7ms다. 첫 HTTP 목록에는 최초 pool 연결 준비도 포함했다.
이는 한 환경의 일곱 쌍이며 통계적 유의성이나 다른 네트워크에서의 같은 개선율을 주장하지 않는다.
기본 `http.proxySupport=override`에서 직접 HTTP를 강제로 켜지 않는다. CLI 경로에서도 위의 큰 snapshot·쿼리 개선은 적용된다.

## Native Git 사전 인증

단위는 ms, 전체 명령 시간의 중앙값이다. 옵션을 켠 표본은 모두 `supported` 판정을 받아 실제 적용됐다.

| 구간 | 기본 | 사전 인증 | 변화 | 개선 쌍 |
| --- | ---: | ---: | ---: | ---: |
| 변경 없는 fetch | 619.1 | 674.0 | 8.9% 느림 | 1/7 |
| 변경 없는 pull | 632.0 | 721.4 | 14.1% 느림 | 2/7 |
| push dry-run | 744.3 | 523.2 | 29.7% 빠름 | 7/7 |

push dry-run은 일곱 쌍 모두 `GET 401 → GET 200` 두 요청이 `GET 200` 한 요청으로 줄었다.
실제 객체 업로드·실제 push 완료 시간의 개선율은 아니다. 잘못된 임시 자격 증명은 401로 실패했고 실제 push는 한 번도 수행하지 않았다.
fetch/pull은 인증 challenge가 없는 공개 읽기여서 개선이 없었다. 첫 legacy fetch에는 추가 POST 두 번이 있었고 이후 fetch와 모든 pull은 GET/POST 각 한 번이었다.
이 초기 fetch 차이도 원자료에 남겼으며, fetch/pull의 속도 개선 근거로 사용하지 않는다.

`gitSimpleCompare.githubGitProactiveAuth=false`를 유지한다. 인증이 필요한 GitHub HTTPS 작업에서 명시적으로 선택하는 고급 옵션으로 남긴다.
API 자격 증명을 native Git에 주입하거나 전역/로컬 인증 설정을 영구 변경하지 않는다.

## 판정

성능 개선은 **반복 목록·상세 파일 재열기·검색에서 확인**했다. cold 목록 개선은 입증하지 못했다.
기본값은 `githubReadTransport=auto`, `githubGitProactiveAuth=false`가 적합하다. auto는 지원을 증명한 정책에서만 HTTP를 사용하고 나머지는 CLI를 쓴다.
HTTP의 추가 효과는 상세·검색에서 확인됐으며 목록은 쿼리·응답 대기가 지배해 4.0%에 그쳤다.
native fetch/pull 전체를 빠르게 한다고 보고하지 않으며 사전 인증을 기본 활성화하지 않는다.

140개 표본, 49개 전체 DTO 비교가 모두 검증을 통과했다. 사용자 저장소의 HEAD/index/config와 native fixture의 HEAD/config가 보존됐다.

## 검증

- 최종 전체 `GSC_VERIFY_PR_RENDERER=1 npm test`: 2,550개 중 2,549개 통과, 실패 0개, 선택 검사 1개 생략. 실행 시간 842,394.250042ms.
- Node 18.20.8: HTTP·요청·인증·라우팅·실제 조립·snapshot 회귀 검사 49개 통과. 공식 Node 배포물의 SHA-256을 확인했다.
- 타입 검사와 production package 통과. production bundle 1,775,649 bytes. GraphQL 16.14.2 parser-only minified bundle 43,272 bytes.
- production dependency audit: 취약점 0개. ESLint 실행 파일이 없어 lint는 종료 코드 127이며 실행 완료로 간주하지 않는다.
- 실제 VS Code 1.144.0 / Extension Host Node 24.22.1에서 공개 HTTP 조회와 검색, CLI 강제, 기본 Agent 정책의 CLI 선택, 로컬 TLS 연결 재사용·소비자 취소 격리·종료 시 close를 확인했다.
- 실제 Settings의 영어·한국어 문자열과 체크박스·드롭다운 전환을 확인했다. 1440×900과 900×700 화면 및 선택 상태를 시각적으로 확인했다. 한국어는 임시 프로필에 공식 Microsoft 언어 팩을 설치해 `vscode.env.language=ko`를 확인했다.
- 프록시·CA·Unix socket·Enterprise는 요청 전 CLI 선택 회귀 검사다. 실제 외부 proxy/Enterprise 서버는 미검증이다. 실제 Host 검증은 1.144.0에 한정하며 최소 지원 VS Code 1.85 Host는 실행하지 않았다.

## 독립 리뷰와 후속 수정

독립 리뷰 1회는 `706d1c2..5390ffa` 범위를 검토했다. Critical 0개, Important 5개와 Minor 1개를 보고했다.
실제 CLI 인증 identity, 제품 drawer의 placeholder 캐시, 리뷰 실패 시 파일 보존, 실패 응답의 문맥 재검증, 미리보기 후속 페이지의 세션 소유권을 수정했다.
상수 0이던 큐 대기 시간은 Important로 재분류해 실제 측정값과 회귀 검사를 추가했다.
모든 수정은 실패 재현 후 통과를 확인했고 전체 검사를 통과했다. 재리뷰를 받았다고 주장하지 않는다. 미룬 Minor와 판단을 유보한 항목은 없다.

추가 실제 실행에서 발견한 혼합 metadata 묶음의 불필요한 stable 필드 재조회, Host의 Agent 교체, 검색의 잘못된 canonical scope key도 회귀 검사와 함께 수정했다.
검색이 CLI에 남아 있던 초기 진단 측정은 중단했고 최종 성능 근거에 사용하지 않는다.

## 실행 판단 기록

1. 기존의 깨끗한 전용 작업 브랜치에서 inline으로 진행했다. 사용자가 구현을 승인했고 별도 native worktree가 없었다. 비용은 이 디렉터리와 별도 checkout의 격리를 얻지 못한다는 점이다.
2. 두 번째 계획 승인을 요청하지 않았다. 이미 승인한 설계와 구현 목표가 범위를 허용했다. 세부 인터페이스 선택이 기대와 다르면 검토 가능한 커밋에서 재작업해야 한다.
3. 상수 0 큐 시간의 심각도를 Important로 높였다. 성능 진단에는 실제 대기 시간이 필요하다. 과한 분류였다면 회귀 검사 하나와 계측 필드 수정 비용을 더 쓴 셈이다.
